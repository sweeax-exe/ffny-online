# Late input refresh design review

Read-only source review of the proposed refresh before the game input producers `sub_00079280`, `sub_0002D9E0`, and `sub_00079FA0`. No runtime edits, builds, or game runs were performed. The toolkit queue is generic; the current consumption adapter and producer wrappers are game-specific.

## Existing delivery contract

The toolkit samples host controls on its input worker (`xboxrecomp-input-latency/src/input/input_host.c:513-588`; poll period is configured at `:45,846-880`). `xbox_HostInputPeekState` reads the retained button edge plus current host state (`:1145-1173`). `input_edges_peek` bounds/reorders the button transitions but does not deliver them (`xboxrecomp-input-latency/src/input/input_edges.c:60-82`). USB marks the token delivered only after an interrupt-IN TD completes successfully (`xboxrecomp-input-latency/src/usb/ohci.c:942-943,972-976`; host callback `input_host.c:1194-1199`). The guest then consumes a matching delivered edge with a newer packet number (`input_edges.c:94-110`, `input_host.c:1202-1212`). A direct host snapshot in the game producer would skip that delivery proof unless it explicitly uses a separately approved contract.

The current GET_REPORT path is deliberately snapshot-only in consumed-edge mode (`xboxrecomp-input-latency/src/usb/usb_gamepad.c:161-166,841-846`); it must not be repurposed as a queued-edge source. Current-state reads carry no delivery token. UI/focus gating is enforced by the host read paths (`input_host.c:1145-1188`).

## What the title code does

`sub_001EBBE0` enumerates up to four XDK handles at `0x003C9340` and calls `sub_0027E075` for each valid handle (`src/recomp/gen/recomp_0013.c:44578-44689`). It converts the report axes and updates persistent button/edge state around `0x003C92C8`, `0x003C92D2`, `0x003C92CA`, and `0x003C92D4` (`:44780-44850`). In particular, the digital rising-edge mask is recomputed from current XOR previous and the current word is then saved. Calling this poller twice with the same report can clear the one-poll rising-edge mask on the second call. This makes a blind synchronous re-poll before the producer unsafe even though the USB FIFO still retains the edge.

The three producer wrappers only add before/after cache observations around their generated functions (`src/recomp_manual.c:203-228`). The generated producer paths perform game-specific mapping into the per-player output structure; for example, `sub_00079280` invokes `sub_000DC4F0` for its controls and writes the mapped values to a player record (`src/recomp/gen/recomp_0003.c:78186-78345`). The producer hook must not replace this mapping or write an independently constructed PAD_TABLE value. The adapter currently preserves XDK's game mapping and distinguishes fighter-acknowledged action controls from Start/Back, which remain API-acknowledged (`src/hooks/input_latency_guest.c:25-35,95-125`).

## Option assessment

**Direct native-host snapshot before the producer: unsafe with the current contract.** `xbox_HostInputCurrentState` returns the latest sampled host value, not a queued edge or USB-delivered token (`xboxrecomp-input-latency/src/input/input_host.c:1177-1190`). Reading it and writing guest state could expose a press that has not completed a USB TD, fabricate packet identity, bypass the game's XDK conversion/deadzone/scaling, and desynchronize the queue's acknowledged mask. Reusing `PeekState` still is not enough: it returns a token, but only OHCI's successful TD path marks that token delivered. A host-side route is viable only if it transports a previously successful, versioned XDK report through the title's existing conversion and does not invent a packet number or advance queue acknowledgement.

**Calling `sub_001EBBE0` synchronously before the producer: preserves USB/XDK provenance, but risks poller side effects.** The normal path can retain guest packet IDs, successful USB delivery, XDK report layout, remapping, axis transforms, and UI/focus behavior. But the extra call re-runs per-handle sampling and updates title-side edge history; same-report repetition can clear the one-shot rising-edge mask. It can also repeat handle/event processing, and it may be redundant if the normal poller already ran this frame. Call order and thread/reentrancy assumptions are not established by the wrappers alone.

## Constraints and review gates for an implementation

- Keep the generic toolkit default disabled and make the game experiment explicit. Do not silently change the USB delivery prerequisite.
- Before adding a guest poll, instrument the current call order and per-handle packet values for `sub_001EBBE0` and each producer. Prove there is one target producer invocation and no poller reentrancy on each tested path.
- Never synthesize or increment guest packet IDs. Treat equal/stale packet reads as duplicates; preserve the existing monotonic packet check and pending-ACK semantics.
- Do not allow a second poll of an unchanged report to erase an unconsumed one-frame edge. Either skip the refresh when no newer report exists, or prove a narrowly scoped cache refresh leaves `0x003C92D2/0x003C92D4` and handle state equivalent to exactly one poll.
- Keep the title's existing XDK report-to-game mapping for digital controls, A/B and Black/White order, triggers, sticks, and scaling. Do not route Start/Back through fighter-step acknowledgement; pause/menu input must remain responsive without a simulation step.
- Reset/cancel the experiment on focus loss, active UI, disconnect, and USB reset using the same policy as existing queues. An in-flight earlier snapshot must not republish after such a transition.
- Review the values read by all three producer paths; do not assume one writer covers the other two or the player/port mapping is identical in every mode.

Minimum validation gates: unit fixture for a button down held across two identical poller invocations (one native rising edge only); fixture for out-of-order/equal packet completion; trace proving each source edge has one successful USB completion followed by the expected newer XDK packet and fighter ACK; game trace comparing before/after cache words and call counts across all three producer paths; axes/Start/Back/menu and focus/UI/hotplug checks. Measure the XDK-completion-to-cache interval before and after and verify fighting behavior on real input; source inspection alone cannot establish a latency improvement.

## Narrow per-device callback candidate

The callback proposal is a better seam than re-running `sub_001EBBE0` or the three producer functions. `sub_000DD930` advances previous/current/repeat state for each connected manager port, calls that object's virtual method at `+4` to fill one local 0x94 report, then calls `sub_000DCE00` and (when active) `sub_000DD770` (`src/recomp/gen/recomp_0006.c:54586-54595,54868-54911`). `sub_000DC970` is a concrete type-2 callback: it checks `this+8` against `0xFFFFFFFF` and `this+0xC == 2`, copies exactly 0x94 bytes from global `+0x17E0 + port*0x94` to the supplied output, and returns 1 (`:51841-51876`). Wrapping it after the generated callback and replacing the output only after both original and XDK success lets the normal `DD930 -> DCE00 -> DD770` transition/filter path run once. It avoids touching the worker queue or producer cache directly.

Static source supports the proposed 0x94 field *shape* and mapping. `sub_000D7BF0` writes 16 eight-byte entries plus four axis floats: the first eight entries have flag byte 1 and float value at `+4` (analog byte times `0x29AF38`, the game's reciprocal-scale constant); the next eight have a 0/2 dword at `+4` with flag byte left 0; axes are copied into `+0x80..+0x8C` (`src/recomp/gen/recomp_0006.c:39831-39967`). Mapping from `sub_001EBBE0` and `D7BF0` source is:

- analog entries: left trigger, White, right trigger, Black, A, B, X, Y; values are each report byte multiplied by the game's scale constant, and those eight entry flags are 1;
- digital entries: Start, Back, left-stick click, right-stick click, then D-pad up/down/left/right; each value is 0 or 2 (the `DCE00` disabled-flag path maps 0 to released and 2 to held; `recomp_0006.c:52793-52828`);
- axes: four signed 16-bit stick values are normalized with the game's add/multiply constants and zeroed below its absolute-value threshold in `sub_001EBBE0`, then copied by `D7BF0`; `DCE00` applies device-specific axis configuration and `DD770` applies its transition/repeat processing. Do not apply the later device deadzone/inversion twice.

This establishes the mapping logic but not byte-for-byte equivalence for every device/configuration. Keep the proposed shadow mode: call the validated XDK getter but preserve the original 0x94 output, independently build the candidate, and compare all bytes for the same successful packet/report before enabling replacement. Include boundary values around the poller's axis threshold, all 16 button entries (especially the nonidentity analog/digital ordering), all four axes/signs, and a range of device deadzone/invert settings. Do not infer equality merely from one-button tests.

The nested XDK call can be guest-thread-aware if it is synchronous inside the callback: `DD930` is in the game update path on the guest caller's TLS, and the existing `sub_0027E075` manual wrapper reads arguments from that TLS guest stack and synchronously runs the generated function before invoking `input_consumption_xdk_end` (`src/recomp_manual.c:191-199`; guest poller call site `recomp_0013.c:44687-44689`). Allocate its 22-byte state buffer and two arguments in guest virtual stack memory, preserve/restore the caller's complete `RECOMP_TLS` register/FPU/SIMD state including original callback `g_eax`, and do not call generated guest code from the host input worker. Validate `this+8` is within the XDK handle table's four ports, resolve and verify the actual handle/context rather than equating manager port, host slot and fighter port, and replace only on status 0 plus report length 18. Keep the original callback output on any invalid port/handle, non-live-fight/UI/focus gate, failed XDK read, or unexpected report length. The host exposes a UI-active getter but no focus getter in its current header; if focus gating is required, add/use an explicit thread-safe query rather than reading private host state (`xboxrecomp-input-latency/src/input/input_host.h:111-117`).

**Reset-generation ACK guard is required before enabling this path.** The host queue reset clears `packet_seen` (`xboxrecomp-input-latency/src/input/input_edges.c:20-25`), but the game adapter's per-slot `pending` record has no reset generation and persists across queue cancellation (`src/hooks/input_latency_guest.c:14-16,66-75,114-125`; host cancellation `input_host.c:1216-1224`). A stale pre-reset pending report whose action mask equals a newly delivered post-reset edge can therefore pass the now-empty packet baseline and acknowledge the new edge. Packet-number monotonicity alone does not protect across reset. Tag pending reports with a host queue generation and reject mismatches, or add a reset invalidation path without taking the adapter lock from under `H.cs`; test focus/UI/config/USB reset followed by a same-button re-press before the next XDK read.

I found no evidence that the proposed nested getter has an asynchronous completion callback: the current manual wrapper invokes generated XDK state-copy code and immediately calls the adapter. Thus an older worker completion overwriting a newer pending record is not established for this synchronous callback design. Still reject stale/older pending packet writes (with reset generation plus serial comparison) and test equal-packet duplicate calls; this is a guard against future/yielding changes and cross-thread assumptions, not a proven current race.
