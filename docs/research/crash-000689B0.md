# Crash in `sub_000689B0`: the front end draws a stale custom-control slot (vtable word = 0xAA53C5AA)

Read-only study (nothing built, run or edited). Sources: lifted C `src/recomp/gen/recomp_0003.c` (the front-end
controls, 0x58000..0x6C200), `recomp_0011.c` (the game heap, 0x183000..0x186000), `recomp_0014.c` (strstr),
`recomp_0001.c` (allocator), `src/recomp_manual.c`, the user's `game/default.xbe` (strings and one vtable), and sliced
reads of two bug-report logs (no log content is reproduced here beyond line numbers and counters).
Tags: **[V]** read in code/log, **[I]** inferred, **[G]** guess.

## 1. What `sub_000689B0` is, and what faults

* [V] It is the front end's **"draw the custom controls named in this movie element" callback**. It is stored in a
  callback table at `0x3B1E58` (`recomp_0003.c:38826`, next to `0x3B1E08 = 0x68BA0`, the FuncCall handler) and is never
  called directly, only through that pointer. It calls `sub_00018C80(0)` at the end, which is where the
  widescreen note found it.
* [V] The global table `0x345248` has **24 slots** of control-object pointers. `sub_00068950(idx, obj)` sets one,
  `sub_00068970(idx)` clears one, `sub_00068990(idx)` reads one, `sub_000685B0` (ctor of the 0x64-byte object made in
  `sub_0006BF90`, FE init) zeroes all 24. Nothing else writes the table (grep over lifted C, `src/`, hooks).
* [V] The function walks the 24 slots twice (pass 1 and pass 2). For each non-null slot it does
  `sub_00200DA0(arg2, obj+4)`, which is **strstr(haystack = element name, needle = obj+4)** (`recomp_0014.c:18233`;
  an empty needle returns the haystack, so it counts as a match). On a match it calls `obj->vtbl[4]` (pass 1,
  `MEM32(MEM32(obj)+0x10)` at `loc_00068AE4`) or `obj->vtbl[3]` (pass 2, `+0xC`, `loc_00068B54`).
* [V] Both crashes: fault address 0xAA53C5BA = `0xAA53C5AA + 0x10`. So `MEM32(obj)` (the vtable pointer) was
  0xAA53C5AA and the call went through `vtbl[4]` in pass 1. `esi` = loop index = 10 (build 39) and 8 (build 24);
  the host offsets +0xF6E / +0xF73 differ only because the two builds compiled it differently.
* [I] `ecx` in the dumps (0x810A5380, 0x800A5A80) is the object pointer `table[esi]`: a 128-aligned address in the
  0x80000000 contiguous-RAM mirror, so it is readable guest RAM, not garbage. `ebx` and `edi` (0x42850000, 0x439BC000)
  are float bits (66.5f, 311.5f) of stack arguments, identical in both runs because the screen geometry is the same.
* [V] Slot meaning (from `sub_0006B110`, `sub_0006B2F0`, `sub_0006BDF0`, `sub_0006B530`, `sub_0006B210`):
  slot 0 `createplayer`, slot 1 `trophies`, slots 3..6 `heroportrait%dctrl` (manager array +0xA8), slots 7..23
  `herothumb%dctrl` (manager array +0xB8, 17 entries; "FE::Choose Character thumb Custom control", object size
  0xAC, vtable `0x297C48`). So slot 10 = `herothumb4ctrl`, slot 8 = `herothumb2ctrl`: **a thumb control both times**.

## 2. Where 0xAA53C5AA comes from

* [V] It is not a poison pattern of ours: no hit in `tools/xboxrecomp/src`, `src/` or `src/hooks`. It is the
  **magic of the game's own heap-block header**: `sub_00185B40` (alloc) writes `MEM32(blk)=0xAA53C5AA`, `blk+4=size`,
  `blk+8=slot in the heap's table`, returns `blk+0x10`, and writes guard bytes `5A F0` after the data
  (`recomp_0011.c:72085`); `sub_00185BF0` (realloc) and `sub_00185CD0` (free) check it and the guards.
  **Free does not clear the magic** (`:72312`), it only zeroes the table entry and hands the raw block back (`sub_001839B0`).
* [I] So `MEM32(obj) == 0xAA53C5AA` means the memory the slot points to is now **the start of a heap block header**,
  not a control object: the object was freed and its address was reused as the start of another heap block
  (128-aligned raw address, so a plausible reuse). A use-after-free (stale slot), not an uninitialised field.
* [I] Why it is rare: a stale slot is only drawn if strstr matches. With the header at `obj`, `obj+4` is the new
  block's size dword; its low byte is 0 when the size is a multiple of 256, which makes the needle empty and
  matches every element (that gives the crash). Otherwise strstr fails and the dead slot is silently skipped for hours.
  [G] (not checked) that pool block sizes are often multiples of 256.

## 3. Who leaves the stale slot (not fully settled)

* [V] Create/destroy are symmetric on paper: `sub_0006B110` (`Battle.StartUserIDThumbCtrl`, method table
  `recomp_0003.c:41703`, handler `sub_0004C130`) makes up to 4 thumbs and registers slots 7..10 if the manager's array
  entry is null; `sub_0006B210` (`EndUserIDThumbCtrl`) and `sub_0006B530` (`EndPortraitCustomCtrl`, also 3..6) call
  `vtbl[2]`, clear the table slot, then `vtbl[0](1)` (delete) and null the manager array entry. `sub_0006BB70` (FE
  shutdown) does both. `sub_0006B2F0`/`sub_0006B110` **skip creating a control whose manager-array entry is
  already non-null**, trusting that it is still alive and registered.
* [V] Log 1 (build 39): 4 Story fights each call `Battle.StartUserIDThumbCtrl` (log lines 2692, 4647, 5817, 8085)
  and **none is followed by `EndUserIDThumbCtrl`** (the only End is at line 1596, before the first fight). The last
  one is at line 8085, then `MemCard.Save(rewards1.swf)`, `Game.Quit()` at 8208, `[SCENE] loading sc14`.
  So the thumbs made by the rewards screen outlive Game.Quit.
* [V] Timeline of log 1: vblank counter 36600 at Game.Quit, 504700 at the crash, about 2.2 hours of play time.
  From line 8508 (just after Game.Quit) the log fills with 44,432 `D3D8: CreateTexture2D failed: 0x80070057 (fmt=15
  256x2)` lines (separate symptom, not studied). The last events before the crash (lines ~53936..54130) are an FE
  reload: `feflow.xml`, `irrad.viv`, `feposes.viv`, `fepose02*.o` (the files `sub_0006B2F0` names), `[MENU] trans/t1`,
  song notification, then the crash on the next frame. So "right after Game.Quit" is not literal: the crash is on the
  first FE frames after the story cinematic and its 2 hours.
* [V] Log 2 (build 24): `Battle.EndPortraitCustomCtrl()` (log line 1682) then `GetScreenInfo(options/battleID.swf)`, crash
  within the next frame or two (no D3D summary line between, line 1688). Slot 8 is in the range `sub_0006B530` unregisters.
* [I] Most likely chain: a thumb control is freed by something other than End/Shutdown (a bulk release of the heap
  region it lives in when the match/cinematic scene is torn down, or a destroy path that nulls the manager array
  but not the table), its table slot and/or manager-array entry stay, the address is reused for a heap block, and the
  next FE frame draws the slot. For log 2 (where End *was* called) a divergence is needed: the manager array entry
  was 0 while the table slot was not, because `sub_0006B530` only unregisters when the array entry is non-null
  (`loc_0006B551`, `loc_0006B587`). [G]
* [G] A thread race is not supported by anything seen: the table is read and written only by guest code on the
  front-end path. Nothing watched it, so this is absence of evidence only.

## 4. Proposed fix

1. **Guard (small, no re-lift).** `sub_000689B0` is reached only through the pointer at `0x3B1E58`, so it can be wrapped in
   `recomp_lookup_manual()` exactly like `sub_00068BA0` (`src/recomp_manual.c:1513`, `funccall_hook`). Wrapper:
   `fe_ctrl_scrub()` then the lifted `sub_000689B0()`. In the scrub, for `i` in 0..23, `p = MEM32(0x345248 + 4*i)`; if `p`
   is non-null and (`p` is outside guest RAM and its 0x80000000 mirror, or `MEM32(p)` is outside the `.rdata` section
   `0x285240..0x2D54E0`, where every control vtable lives), set the table slot to 0 and log once per index:
   `[FE] stale custom control slot %d (obj %08X vtbl %08X)`. The `0xAA53C5AA` case is covered by the range test. [I] This
   removes the crash, but the manager array entry (`+0xB8`/`+0xA8`) stays non-null, so a later `Start*` will not
   recreate that control: the thumb is missing, not a crash. To fix that too the scrub needs the manager (`sub_00012CF0`
   registry entry 0xD, the `0x2FB148` singleton) and should null `mgr+0xA8+4*(i-3)` / `mgr+0xB8+4*(i-7)` and the copies
   at `mgr+0x9A18` / `mgr+0x9A28`.
2. **Root cause** (after the diagnostic below shows the freeing path): make create/destroy symmetric, e.g. at
   `Game.Quit()` (`funccall_hook`, `src/recomp_manual.c:1276`) call the game's own `sub_0006B210` on the manager when a
   Story rewards screen left thumbs alive, so a heap release never frees an object that is still registered.
3. No allocator or poison change: the toolkit has nothing to do with this value.

## 5. How to reproduce / confirm (no run was made)

* Diagnostic first (env-gated, in `funccall_hook` after the FuncCall): print `table[3..10]`, and for each non-null slot
  whether `MEM32(p)` is in `.rdata` and whether `MEM32(p-0x10)` is the block magic. Run Story (a fixture via
  `scripts/scenarios.py fixture add NAME --story ID`, or `harness.py` with `getscreeninfo(story/...` anchors), finish a
  fight to `battle/rewards1.swf`, `Game.Quit`, let the cinematic end or skip it, return to the FE hero/venue select
  (`battle/chsVenue.swf`). If the theory holds: after `Game.Quit` slots 7..10 are non-null and when the FE reloads their
  `MEM32(p)` is no longer a vtable.
* `RECOMP_WATCH_WRITE=0x345248+4*10` with `RECOMP_WATCH_WRITE_LEN=4` (docs/agent/diagnostics.md) names who sets and clears
  slot 10; a second watch on the object address (`p+0`) names the next writer after the free. A hit is evidence, a miss is not.
* Battle route (log 2): Battle mode, `battle/chooseF2.swf` with 2+ players, accept, watch `EndPortraitCustomCtrl` then
  `options/battleID.swf`, repeated with the same diagnostic. Expect rarity (two sightings in 14 builds).
* [G] Forcing it: in a test build, after `EndPortraitCustomCtrl`, write `0xAA53C5AA, 0x100, 0, 0` over one thumb object's
  address and confirm the guard logs and survives.
