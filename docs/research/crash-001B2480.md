# Crash in `sub_001BBC10`, called from `sub_001B2480` (the attack-parts walk of WrestlerSpecInit)

Read-only study. Nothing was edited, built or run. Sources: the lifted C in `src/recomp/gen`
(`recomp_0012.c` unless a file is named), `recomp_0004.c`/`recomp_0005.c` for the load path, the XBE image
`game/default.xbe` (only the table at `0x2F3640` and strings), and the user's own `game/motion/main_all.dat`
(decoded offline to check the value range; no bytes are reproduced here, only ids and counts).
Line numbers are `src/recomp/gen/<file>:<line>` in the current tree.

Tags: **[V]** read in code or data, **[I]** inferred (reasoning given), **[U]** not settled.

**2026-10-25: tested and explained, see section 11.** Teck, Santos, O.E and Eric Sermon crash every
Battle-mode match load, the first one included: the game's match set-up has no entry for them, so their
character index stays -1 and their model name empty. A stale model from an earlier match turns the crash
into the WrestlerSpecInit one read below (character index -2, the same `edi = 0x3FFE`). Sections 6 and
9.4 (a memory overwrite) do not apply to these crashes.

## 0. Short answer

1. `esi = 0x003BA5C8` is **fighter record, slot 1** (`0x3B92E0 + 1*0x12E8`). Its first word `0x003B92E0` is the
   pointer to its opponent's record (slot 0), which `sub_001B3110` stores for a two-player match. [V]
2. `sub_001B2480` is the per-move step of **WrestlerSpecInit** (the game's own debug strings say
   `WrestlerSpecInit(P%d)` and `waza spec %3d: ... atk-parts(%d %d %d)`). It runs on purpose during every match load
   (and on a rematch restart), once per active slot, for 66 moves, before the first simulation step. [V]
3. The three bytes `record+0xF74..0xF76` are the three **"atk-parts" ids** of the move that was decoded a moment
   earlier: 5-bit fields unpacked from `main_all.dat` by `sub_001A3630`. They index a 23-entry table of joint lists at
   `0x2F3640`. Valid values are 1..22 (index 0 is a NULL entry). [V]
4. In the shipped data **every** (character, move) pair used by this code decodes to 1..22. So an out-of-range byte
   is not data; it means the decode read the wrong bytes (wrong or stale table pointers, a buffer that was
   overwritten or freed, or a bad character index). [V for the data, I for the consequence]
5. From the register dump the byte can only have been **28 or 31** (if it came from the 5-bit decode), see section 4. [V]
6. The per-record bytes cannot be "left over" from the earlier match: the whole record is zeroed at every match
   set-up and the bytes are re-decoded immediately before each use. What *can* be left over is the set of
   **global table pointers** (`0x3B85D8..0x3B8F18`) that point into the `main_all.dat` block, which the match
   teardown frees without clearing them. The load path re-parses them before WrestlerSpecInit, so the working
   theory is not "stale" but "the block was overwritten between the parse and the use" (section 6). [I]

## 1. What object is `0x003BA5C8`, and who passes it in

* Fighter records: 4 records of `0x12E8` bytes at `0x3B92E0`..`0x3BDE80`; slot at `+0x28`, character index at `+0x2C`
  (`docs/research/fighter-record-fields.md`). `0x3BA5C8 - 0x3B92E0 = 0x12E8` so slot 1. [V]
* Created in `sub_001A4D90`: the four records are zeroed (`recomp_0012.c:11950-11953`, `ecx=0x12E8`, `edi=0x3B92E0`),
  then for each slot `i` with `MEM32(0x3B90B8+4*i) != -1` it calls `sub_001B3110(record, i, 0x3B90B8[i])`
  (`:11962-11968`), else it stores `-1` at `record+0x28`. `sub_001B3110` stores slot at `+0x28` and the character
  index at `+0x2C` (`:49607-49608`) and, for two players, `record+0` = the other record (`:49765-49774`). [V]
* `0x3B90B8[slot]` = `setup[+0xA8+4*slot] - 1`, copied from the match-setup block in `sub_000871F0`
  (`recomp_0004.c:7510` region, the per-player loop). So `+0x2C` is the zero-based character index, 0..140 for the 141
  entries of the per-character table (section 2). [V]
* Who passes it to `sub_001B3490` / `sub_001B2480`:
  * `sub_001A2EA0` (`:7262`): loop `esi = 0x3B92E0 .. < 0x3BDE80`, `edi = slot`; when `MEM32(esi+0x28) != -1` it calls
    `sub_001B3490(slot)` (`:7304`, ret `0x001A2ECD`) and then `sub_001B2130(esi)` (`:7308`). Slot 0 runs first, so
    **slot 0 had already gone through all five loops without a problem** when slot 1 crashed. [V]
  * `sub_001B3490` (`:50011`) rebuilds the record pointer from its stack argument (`:50030-50047`: `esi = slot*0x12E8
    + 0x3B92E0`) and calls `sub_001B2480` with `esi` still holding the record (register convention): five loops,
    calls at `:50094` (group 0), **`:50201` (group 1, ret `0x001B3778` = the crash)**, `:50245` (group 2),
    `:50309` (group 3), `:50371` (group 4). [V]
  * `sub_001A2EA0` is called only from `sub_000C8820` (`recomp_0005.c:91149`, ret `0x000C88C6`), which is called
    by the full-init `sub_0008B730` (`recomp_0004.c:18195`, after the AI manager `sub_000C9110` at `:18186`) and by
    the rematch/restart `sub_000891A0` (`recomp_0004.c:12273`). [V]

Arguments of `sub_001B2480` (three stack words, `esi` = record): `arg0` = the move's `+0xFB4` value (an animation key; for
group 0 the constant animation ids `0x277C..0x2785`), `arg1` = running index 0..0x4A, **`arg2` = mode 0..4** (loaded into
`edi` at `:47758`, reloaded at `:47810`). The jump table at `0x1B28C0` (`:47923-47934`) sends mode 0/2 to code that does not
touch the joint-list table, and modes 1, 3, 4 to the three table walks (`:47965`, `:48115`, `:48195`). The crash is mode 1
(group 1 of `sub_001B3490`, move ids `0x36..0x63` and `0x6A..0x6D`, counter 5..0x36). [V]

## 2. The bytes `+0xF74..+0xF76` and the table at `0x2F3640`

Writers (searched `0xF74/0xF75/0xF76` and the neighbouring offsets in all `recomp_*.c`): there is **no direct store** to
those three bytes anywhere. They are written only as part of a 0x40-byte struct at `record+0xF6C`:

* `sub_001A3630(dest, src)` (`:8396`): clears 16 dwords at `dest` (`:8418-8421`), resets the bit reader
  (`MEM32(0x3BE104)=MEM32(0x3BE108)=0`) and unpacks fields with `sub_001A3530` (`:8209`, MSB-first bit reader,
  mask table `1,3,7,0xF,0x1F,...`). Field widths in order: 8, 6, 6, 7, 4, 3, 3, **5, 5, 5**, 5, 3, 4, 6 ... stored at
  `+0, +2, +3, +4, +5, +6, +7, +8, +9, +0xA, +0xB, +0xC, +0xD`. So `+8/+9/+0xA` (record `+0xF74/F75/F76`) are the
  three **5-bit** fields (stores at `:8496`, `:8506`, `:8513`). Values are 0..31 by construction. [V]
* Callers of `sub_001A3630`: `sub_001B4930` (`:53433`, `:53482`, `:53516`) and `sub_001B4B20` (`:53629`, runtime). [V]
* `sub_001B4930(record, record, moveId)` (`:53342`) sets `+0xF50 = moveId`, `+0xF54/+0x1020/+0xF5C = waza index`, and for
  moves above `0x29` takes the **4A09 path** (`:53452-53490`): `ptr2 = MEM32(0x3B8654 + (record+0x2C)*16)`,
  `w = u16[ptr2 + moveId*6]`, `wazaIndex = w & 0xFFF`, `src = wazaIndex * MEM32(0x3B85DC) + MEM32(0x3B85EC)`,
  `sub_001A3630(record+0xF6C, src)`. Also sets `+0xFB4 = u16[ptr2+moveId*6+2] + slot*1000`. [V]
* `sub_001B4BA0(record, moveId)` (`:53671`) is the existence test used before each decode: false for id 0, otherwise
  `u16[ptr2 + id*6] != 0xFFFF`. [V]
* Record clears: the whole record at `sub_001A4D90` (`:11950-11953`) and the 0x40-byte struct at the start of each
  `sub_001A3630`. [V]

Readers (all use the same table, so the range assumption also holds during a fight): `sub_001B2480` (`:47775-47777` print,
`:47966`, `:48116`, `:48196`), `sub_001C6440` (`:95889`, `:96196`, `:96339`, the runtime attack evaluation),
`sub_001C5E90` (`:94389`, special-cases `0x14..0x16`), `sub_001D61A0` (`:141263`), `sub_001D69F0` (`:142112`). [V]

The table:

* Address `0x2F3640`, **23 dword entries, indices 0..22**, each a pointer to a `-1`-terminated list of joint indices
  (joint copies live at `record+0xDC+12*j`, 20 joints). Index 23 (`0x2F369C`) is the next structure (`5, 1, -1, ...`). [V]
* It lies in the initialised part of `.data` (VA `0x2D54E0`..`0x2FAFE8`, raw file offset `0x2E3160`). The only references in
  the lifted code are the four loads (`:47967`, `:48117`, `:48197`, `:95890`); there is no store. [V]
* Contents (joint ids): 0 = NULL; 1 = `[1,2,0xE,0x11]`; 2 = `[2,1,3]`; 3 = `[3,2,5]`; 4,5 = `[5,3]`; 6..9 = `[9,8,7]`;
  10..13 = `[0xD,0xC,0xB]`; 14..16 = `[0x10,0xF,0xE]`; 17..19 = `[0x13,0x12,0x11]`; 20 = `[0xD,0xC,0xB,9,8,7]`;
  21 = `[0x13,0x12,0x11,0x10,0xF,0xE]`; 22 = the 15 joints `[5,3,1,0xD,0xC,0xB,9,8,7,0x13,0x12,0x11,0x10,0xF,0xE]`. [V]
* Index 0 yields `edi = 0` and then `MEM32(0)`; the loop only ends on a `0xFFFFFFFF` word. So 0 is only safe if guest
  address 0 holds `-1`. On the real console and in the runtime's thread block that is the SEH chain end
  (the toolkit template `tools/xboxrecomp/templates/runtime/xbox_memory.h` documents a fake TIB at VA 0 with `[0x00] = 0xFFFFFFFF`; this build gives threads their own TIBs, `kernel_bridge.c:589`) [I, not confirmed for this build]. Shipped data never
  decodes to 0 in this code path anyway (below).

Normal range, from the data: I replayed `sub_001A47B0` (the parser of `main_all.dat`) and `sub_001A3630` offline
(algorithm in section 7). The file layout walk ends exactly at the end of the file (a check that the parse is right).
For **all 141 characters x all 66 move ids** of groups 1, 3 and 4 (7130 present entries, 2176 absent), the three parts
are always in **1..22** (values seen: 1-5, 7-9, 11-22). No 0, nothing above 22, no move id past the end of a character's
list, no waza index past the record area. [V]

## 3. When can the byte be out of range at this point

The inputs of the decode are (a) `record+0x2C`, (b) the parsed global tables `0x3B85D8..0x3B8F18`, (c) the loaded
`motion/main_all.dat` block those tables point into, (d) the bit-reader globals `0x3BE104/0x3BE108`. Nothing else.

* Venue data: not an input. The venue only reaches this through `0x3B9084` and the crowd/camera code; the 5-bit fields do
  not depend on it. [V]
* AI data (`ai.viv`): not an input to the decode. It matters only as a possible *clobberer* of memory (section 6). [V]
* Number of players or CPU/human: only decides which slots are active (`+0x28 != -1`) and `record+0` (opponent). The CPU flag
  (`+0x937`) is not read by the decode. [V]
* Stale per-record bytes: ruled out for modes 1/3/4: `sub_001B4930` re-decodes the struct immediately before every
  `sub_001B2480` call (`:50194` then `:50201`; same in the other loops), and `sub_001A3630` clears it first. Mode 0 and 2
  (the only calls with no preceding decode, group 0, `:50094`) do not read the table. [V]
* Read "before it is initialised for the new match": the records exist (zeroed and filled by `sub_001A4D90`, which runs in
  `sub_000871F0` before the AI init and before `sub_000C8820`), so `+0x28`/`+0x2C` are valid when `sub_001A2EA0` runs. [V]
* Wrong or garbage character index: `+0x2C` is `setup[...]-1`; `fighter.xml` `coreID` is 1..141, so the index is 0..140 and
  the 141-entry table (`0x3B8648`, stride 0x10, built by `sub_001A47B0`, loop `:11038-11057`, end `0x3B8F18`) covers it.
  An index of 141 or more would read `0x3B8F24`+ (zero or float bits) and decode record 0, which is still in range, so this
  alone does not produce 28/31. [V/I]
* What does produce an out-of-range 5-bit value: `src` pointing at bytes that are not a waza record: stale/dangling
  `MEM32(0x3B85EC)`/`MEM32(0x3B85DC)`/`MEM32(0x3B8654+16*c)`, or the block they point into having been overwritten or freed. Slot 0 completing proves the
  tables were right for slot 0's character, so the damage is either specific to slot 1's character region or happened
  part-way (a late write), or slot 1's pointer chain is wrong. [I]

Is `sub_001B2480` meant to run in the load? Yes. `sub_001A2EA0` is the "wrestler spec init" stage of
`sub_000C8820`, between the AI set-up and the first step; it precomputes per-move reach/hit/angle values from the joint
distances (`sub_001BBC10`/`sub_001BBC40` over the lists of atk-parts) and writes them to `record+0x2EC/0x2F0/0x9C/0xBCC...`
(`:47856-47857`, `:48292-48306`). The debug prints are compiled out in the retail build (`sub_00011520` is a bare `ret`,
`recomp_0000.c:2960`), so the "waza spec" lines never appear in a log. [V]

## 4. What the register dump says about the byte

Dump: `eax=0xFA3BA6A4 ecx=ebx=0x003BA60C edi=0x00003FFE esi=0x003BA5C8`. `sub_001BBC10` (`:70597`) does not touch `edi`, so
`edi` is the list pointer of the caller.

* The faulting address: list value `v = 0xFF800000`, `esi + 12*v + 0xDC = 0x3BA5C8 + 0xFA000000 + 0xDC = 0xFA3BA6A4`. [V]
* The list pointer advances by 4 each item (`:48074-48077`), so `edi = start + 4*k`. `0x3FFE` is 2 mod 4, so `start` is
  2 mod 4. [V]
* Enumerating the signed-byte index range -128..127 against the table image (script in the scratchpad, results here): a start
  that is 2 mod 4 and reaches `0x3FFE` needs the slot to hold `2` or `0x12` (or a few other small values in floats and lists
  below the table). For a byte that came out of the 5-bit decode (0..31) the only matches are **index 28** (slot `0x2F36B0`
  = 2, 4095 iterations) and **index 31** (slot `0x2F36BC` = 0x12, 4091 iterations). Indices 23-27, 29, 30 would start at
  5, 1, -1, 1, 0x10, 0x11, 3 and cannot end at `0x3FFE`. [V]
* So: the walk ran about 4000 dwords through guest low memory (each one used as a joint index, harmless while the words were
  zero or small) until it met `0xFF800000` at `0x3FFE` (a -inf float, bytes `00 00 80 FF` at `0x3FFE..0x4001`). That is
  expected for a bad index: the lists are only terminated by `-1`. [I]
* 31 (all five bits set) is the more telling value: a 5-bit field read from `0xFF` bytes, e.g. memory filled with `0xFF` or a
  `-1` sentinel region. 28 is equally possible. If instead the byte had been sign-extended garbage (0x80..0xFF) the
  candidates would be -2, -6, -22, -37 and similar; a decode never produces those. [I]

## 5. What to read from a crash dump or log to settle it

At the faulting moment these guest values are enough (all in guest memory, readable from the crash block or a
`peek-guest` style dump):

* Record `0x3BA5C8`: `+0x28` (slot), `+0x2C` (character), `+0xF50` (move id, `0x36..0x77`), `+0xF54` (waza index),
  `+0xFB4`, and the 16 bytes at `+0xF6C` (the decoded struct; `+0xF74..F76` are the atk-parts).
* Globals: `MEM32(0x3B85DC)` (record size, expected 0x20), `MEM32(0x3B85EC)`, `MEM32(0x3B8654 + 16*char)`,
  `MEM32(0x349760)` (the `main_all.dat` block), `MEM32(0x3B85E4)` (expected 0x31).
* Expected values: base `= block + 0x14 + 4*0x31 = block + 0xD8`; record size 0x20; waza index `< 825`. Offline decoding of
  `(char, move id)` gives the value the byte should have had (always 1..22). If the runtime bytes at
  `MEM32(0x3B85EC) + wazaIndex*0x20` differ from the file's, the block was overwritten; if the globals do not equal
  `block + ...`, the parse was stale or skipped.

Cheapest instrument: `RECOMP_WATCH_WRITE` over the waza record area (`MEM32(0x3B85EC)`, length about 0x6700) armed after
`sub_001A4D90`, read with `scripts/guest-stack.py`; or an `sub_001B2480_enter` hook that logs the lines above when any of the
three bytes is outside 1..22 (re-lift needed). Do not clamp the bytes as the fix: garbage waza specs also feed the
hit/range values the AI and `sub_001C6440` use, so a PC with a damaged block would also fight differently from its
peer (a lockstep desync), only without the crash.

## 6. Anything that points at state left from the earlier matches

What persists across matches in the session (match 1 -> Rematch -> menus -> match 3), and what does not:

* **Resets every match**: the four fighter records (`sub_001A4D90`, `:11950-11953`), the 0x40-byte spec struct
  (`sub_001A3630`), the bit reader (`:8418`...), `this+0x30040` (restart counter) in the full init (`recomp_0004.c:17830`).
* **Persists, reused by a rematch**: the parsed waza globals. `sub_001A4D90(counter)` parses `main_all.dat` only when its
  first argument is 0 (`recomp_0012.c:11852-11868`: `cmp arg0, 0` / `jne` over `sub_00044170` + `sub_001A47B0`). The argument is
  `this+0x30040` (`recomp_0004.c:7699-7709`). The rematch/restart `sub_000891A0` does `++counter` (`:12152-12159`), so it
  reuses the tables from match 1 and does not reload the file; the full init `sub_0008B730` zeroes the counter (`:17830`),
  loads `motion/main_all.dat` with `sub_001E46E0` (`:17865-17883`, stored at `this+0`, i.e. `MEM32(0x349760)`) and re-parses.
  The crash chain contains `sub_0008B730`, so the third match took the full-init path with a fresh load and a fresh parse. [V]
* **Dangling after teardown**: `sub_00089310` frees the block (`recomp_0004.c:12664` `sub_000294D0(MEM32(esi))`, then
  `MEM32(esi)=0`) but nothing clears `0x3B85D8..0x3B8F18`. They are dangling between a teardown and the next
  full-init parse, i.e. only during that window. [V]
* **Order in the full init** (`recomp_0004.c`): `main_all.dat` loaded (`:17870-17883`) -> `sub_000871F0` (`:18139`;
  sets up the match globals, calls `sub_001A4D90` which creates the records and parses the tables) -> ... ->
  `sub_000C9110` (`:18186`, the AI manager: opens the AI archive `assets/ai/ai.viv` [I, via `sub_001E3CB0`] and loads `assets/ai/%s.ai` and `.xml`
  files with the **same loader** `sub_001E46E0`; `recomp_0005.c:92613`) -> `sub_000C8820` (`:18195`) ->
  `sub_001A2EA0`. The crash therefore happens right after the AI files are read, which matches the user's observation. [V]

So nothing in the record or the tables is a plain "leftover value"; the two live possibilities are both about memory:

1. **The `main_all.dat` block (about 276 KB, `this+0`) was overwritten or reallocated after the parse**, with the AI loads
   (same loader and allocator, `MEM32(0x2F820C)`) the first suspect, because the timing fits and because the result of
   reading outside the waza records can be any bytes, including `0xFF` runs. A heap problem that needs two teardowns to show
   (free list state after match 1, the rematch, the results-to-menu teardown) would explain "third match". [I, no direct
   evidence yet; compare the block's address with the buffers `sub_000C9110` gets]
2. **A bad `ptr2`/character index for slot 1 only** (slot 0 passed): possible if `0x3B90B8[1]` or the table entry for that
   character is wrong; needs the dump values in section 5. [I]

Ruled out: shipped data out of range; stale spec bytes in the record; the skipped-parse restart path (not on this call chain);
venue/AI contents as inputs; the table at `0x2F3640` being modified (no stores, and the observed `edi` is explained by an
unmodified table and an index of 28 or 31); a lifter flag error in `sub_001B2480` itself (the mode switch, the `-1` test and
the `ebp` loop at `:47959-48098` match the disassembly shape: `ebp` is a function local, `edi` is reloaded from the stack
at `:47810`).

## 7. Offline decoder (to recompute the expected atk-parts for any character and move)

Layout walk of `main_all.dat` (`sub_001A47B0`, `:10963`), `b` = file start, `u32` little endian:

```
tag = "WAZA"; sec1 = b; stride = u32(b+8); count = u32(b+0x10); base = b + 4*count + 0x14   # 0x3B85DC, 0x3B85EC
b2 = b + u32(b+4) + 8;  b3 = b2 + u32(b2+4) + 8;  b4 = b3 + u32(b3+4) + 8
b5 = b4 + u32(b4+4) + 8; b6 = b5 + u32(b5+4) + 8; cur = b6 + u32(b6+4) + 8
for c in 0..140:                      # entries at 0x3B8648 + 16*c, loop ends at 0x3B8F18
    s1 = u32(cur+4); cur += s1 + 8                     # first block (entry +4 = payload)
    s2 = u32(cur+4); ptr2 = cur + 8; cur += s2 + 8     # second block: 6-byte move entries (entry +0xC = ptr2)
w  = u16(ptr2 + id*6)               # 0xFFFF = move absent; wazaIndex = w & 0xFFF (bit 15 -> record+0xF68)
src = base + wazaIndex * stride
# MSB-first bit reader (sub_001A3530), widths 8,6,6,7,4,3,3,5,5,5,5,3,4,6; atk-parts = fields 8..10 (0-based 7..9)
```

Move ids used by `sub_001B3490`: group 1 (mode 1) `0x36..0x63, 0x6A..0x6D` (`:50117-50169`), group 2 (mode 2)
`0x2A..0x2D` (`:50225-50228`), group 3 (mode 3) `0x6E..0x77` (`:50267-50276`), group 4 (mode 4) `0x64..0x69`
(`:50333-50338`). Groups 1, 3, 4 use the joint-list table.

### 9.1 The restart counter (Q1)

* It is `this+0x30040` of the game object (`this = 0x349760`, so guest `0x379DA0`). [V]
* Writers: the constructor `sub_0008CB90` sets 0 (`recomp_0004.c:21737`); the full init `sub_0008B730` sets 0 as one of its
  first stores (`:17830`, before the file load at `:17865` and before the call to `sub_000871F0` at `:18139`);
  the restart `sub_000891A0` does `++` (`:12152-12159`). Nothing else writes it (all `0x30040` references in the gen code:
  `recomp_0004.c:7701, 12152, 12159, 12268, 17830, 18191, 21737`). [V]
* Readers: `sub_000871F0` passes it as arg0 of `sub_001A4D90` (`:7701-7709`), where `0` means "parse `main_all.dat`";
  `sub_000C8820` takes it as arg1 (`:12268`, `:18191`) and uses it only to pick difficulty-scaled values

* Consequence: on the call chain of both crashes (`sub_0008B730` -> `sub_000C8820`) the counter is **always 0 at the
  parse**, because the same function zeroes it shortly before. Neither the menu path nor automatch can leave it non-zero for
  a full init, and nothing on a "back to the menu / new Battle match" path needs to reset it. The case "stays non-zero, parse
  skipped, globals point into a freed block" cannot happen on a full init. [V]
* The only way to get a skipped parse is the restart path `sub_000891A0` (flag `0x400` in `this+0x2B9EC`, tested in
  `sub_0008BB00` at `recomp_0004.c:18432-18460`). There the old block is still allocated (it is freed only by the
  teardown, 9.2), so the tables are not dangling either. Case 2 had no rematch at all. [V]
* What automatch skips compared with the menus (it replays the same FuncCall strings, so the game-side state it sets is the
  same): the `battle/chooseF2`, `chsVenue` and `oldMLoad` screens (FE movies loaded and released, about ten frames before
  `Game.StartGame`), `Audio.StopMusic/FadeMusic`, `Battle.SetCPViewportCam(2,1)`. `Game.StartGame` is called synchronously
  from inside one FuncCall, from the `battle/cmtype` or main-menu screen. None of these touch the waza globals or the
  counter; they change the heap traffic and the timing around the load. [V for what is skipped, I for the effect]

### 9.2 Allocation and lifetime of the block (Q2)

* Loaded in `sub_0008B730` (`recomp_0004.c:17865-17883`): `sub_001E46E0("motion/main_all.dat", 0x400)`, stored at
  `this+0` (= `MEM32(0x349760)`). Size 282904 bytes (the file size). [V]
* Allocator: the file layer calls through two function pointers `MEM32(0x2F820C)` (alloc) and `MEM32(0x2F8210)` (free),
  set once by `sub_001E5860` (`recomp_0013.c:613-614`) from `sub_0001A920` (`recomp_0000.c:28585`) to
  `sub_00029500` / `sub_000294D0`. `sub_00029500` (`recomp_0001.c`, after `:9490`) sends requests of up to 0x400 bytes to
  the small-block allocator object at `MEM32(0x33DB54)` and anything larger (this block) to `sub_001E9E90` ->
  `sub_001E9AB0`, the game's own pool heap in guest memory: 16-byte chunk header with a pool tag at `-14` (indexing
  `0x3C9158`), coalescing free (`sub_001E9F90`), a free hook at `MEM32(0x3C9148)`. It is a normal first-fit/coalescing
  heap with no poisoning, so a freed chunk is reused as it is. [V]
* Freed in exactly one place: the teardown `sub_00089310` (`recomp_0004.c:12664`: `sub_000294D0(MEM32(this))`, then
  `MEM32(this)=0`, then `sub_000C88D0` releases the AI manager). Its only caller is the match state machine
  `sub_0008BE60`, state 15 (`recomp_0004.c:19000-19040`): if `this+0x2B9EC & 0x400` is clear it calls `sub_00089310` and then
  `sub_0008BB00` (new full init); if set (rematch) it calls `sub_00086F40` and `sub_0008BB00` (restart, no teardown). [V]
* So the block is **not** freed at the end of a match or when leaving battle mode. It lives until the start of the next
  non-rematch match, where it is freed immediately before `sub_0008BB00` loads the new one. The new 276 KB request is then
  very likely to be handed the chunk that was just freed (or a coalesced neighbour). The old match's other resources (arena,
  characters, AI buffers) are freed in the same teardown, so the new load runs against a heap with fresh holes. [I]
* Can a later `ai.viv`/`.ai`/`.xml` load land in the block? Not while it is allocated: the AI loads
  (`recomp_0005.c:92613+`, same `sub_001E46E0`) come after `main_all.dat` in the same init and get other chunks. They overlap
  it only through an allocator error or a write through a stale pointer from the previous match's memory. I found no
  flag-validity hazard (`_fv = 0` followed by a published-flag branch) in the heap or loader code (scan of all
  `recomp_00*.c`: five functions match the pattern, none in `0x29xxx` or `0x1E4xxx-0x1EDxxx`). [V for the scan, U for the rest]

### 9.4 Most likely mechanism and the cheapest check

Mechanism (inference): at the next match's start the teardown frees the old block and the old match's resources; the new load
reuses those chunks. Either an old-match owner still holding a pointer into freed memory writes into one of them, or an
allocation overlaps, and the `main_all.dat` block (waza records) is overwritten after the parse and before `sub_001A2EA0`,
i.e. during the AI init that reads `ai.viv`. Slot 0's spec init finishes because its character's records lie elsewhere in the
block; slot 1's are hit. A first match never has freed chunks to reuse, which fits "never on the first".

Cheapest check (no rebuild, no code change): `scripts/peek-guest.py`-style polling of the live process during the second
load. Read `MEM32(0x349760)` once it is non-zero, then read the first `0x6800` bytes of the block (`"WAZA"` at +0, `0x20` at +8,
`0x31` at +0x10, records from `block+0xD8`) repeatedly and diff against `game/motion/main_all.dat`. If the bytes change between
the parse (end of `sub_000871F0`) and `sub_001A2EA0`, the block is overwritten; the changed range and its contents (compare with
the AI files) name the writer. A second run with `RECOMP_WATCH_WRITE=<block+0xD8>` and `_LEN=0x6700` (the address repeats when
the heap behaves the same) gives the writer's registers and stack. Also log the block address of each match: an address equal
to the previous match's confirms same-chunk reuse. If the block is intact at that point, the cause is the pointer chain for
slot 1 (read `+0x2C`, `+0xF54`, `0x3B8654+16*c`), the second candidate in section 6.

### 11.2 Why

* `sub_00109F80` is the game's ELF object loader ("dlopen": the section types it accepts are ELF ones, the
  section count is the halfword at `+0x30` of the image). The fighter models are ELF objects in
  `assets/v2ip.viv` (`V2IP_305A.o` for Teck), and those four files are well formed (6 sections, the same
  shape as Doc's). [V]
* The image it parsed was not a model: the registry lookup in `sub_00026A00` (`sub_0006EF20`, a list keyed
  by image) found nothing and its result is not checked, so the parse started at guest address 0 and read
  the section headers out of the code (the `0xCCCCCCCC` padding in the "section types"). [V, with entry
  probes on `sub_00026A00`, `sub_0006EF20`, `sub_00097710`, `sub_0008C9E0`]
* Nothing was loaded because the model name was empty. The match set-up block (the pointer at game
  `+0x2FF5C`) holds, per slot, arrays read by the match init `sub_0008B440` and by `sub_000871F0`:
  `+0xA8` and `+0xC8` the coreID, `+0xE8` the speechID, `+0x108` the bodysize, `+0x148` the model name,
  `+0x158` the internal name, `+0x168` the shadow name, all as in `fighter.xml`. For WC the slot holds
  24, 24, 31, 2, "V2IP_303A", "WC", "V2SD_3EA". For Teck the coreID is -1 and the rest is empty in a
  session's first match; in a later match the string fields still hold an earlier fighter's values
  (Doc's model was loaded twice in the Doc-and-Teck match). [V, dumped at the entry of `sub_000871F0` and
  `sub_0008B440`]
* With a stale model the load gets past the model, and the character index of the fighter record is
  coreID - 1 = -2. WrestlerSpecInit then reads the waza list pointer from `0x3B8654 + 16 * -2`, which is
  not a list, decodes garbage atk-parts and walks the joint table into low memory: the crash of sections
  0-4. Shown directly: with the model and shadow written into Teck's slot by hand (coreID left at -1) the
  crash moves to `sub_001BBC10` with `edi = 0x3FFE`, the exact value of the players' dump. [V]
* So both players' crashes with Teck (later matches, WrestlerSpecInit) and the build-13 reports of a
  crash at every load are this one cause. The heap theory of sections 6 and 9.4 is not needed for them.
  It does not explain case 2 of section 9 (Starks and Crow1, no story fighter), which stays open. [I]
* Why the slot stays empty: Battle mode never offers these four (no select portrait, and the FE-to-
  backend fighter lookup that `Controller.ControllerSetup` runs, `sub_000558E0` -> registry 0x19
  `sub_000DCB20`, has nothing for them), so no backend record is copied into the set-up. [I: the lookup
  was read, not traced to the copy]

### 11.3 Can it be fixed

An experiment (entry hook on `sub_000871F0`, not committed) wrote Teck's `fighter.xml` values into his
empty slot: coreID 70 into `+0xA8` and `+0xC8`, speechID, bodysize, and pointers to the game's own
"V2IP_305A" and "V2SD_2EA" strings (found in the parsed fighter data in the heap). Teck then loaded and
fought a full match as player 1 (character 69, health 291.2). It is not a fix yet:

* the slot has more fields that differ between a resolved and an unresolved fighter (`+0xB8` is 1 for WC
  and 0 for Teck, a mask at `+0x198` is 7 against 3, the internal name at `+0x158`), whose meaning is not
  known;
* only one fight was played, with Teck in slot 0; Teck as the CPU in slot 1 was not tried with the fill;
* the hub could still not offer them: the fighter grid shows only fighters with a portrait in the online
  art, and these four have none. They would appear only as the CPU that fills a mode.

Until the set-up copy is found and replayed for them (or every field is known), they stay out of every
online list (`src/hooks/online_data.c`) and the relay keeps replacing them (`UnsafeFighters`).
