## What a successful guest read identifies

`sub_001EBBE0` is a four-entry gamepad poller. It initializes the output/handle table base to `0x003C9340`, advances its entry pointer by `0x90`, and stops when the corresponding byte offset reaches `0x240` (four entries). Its loop counter starts at zero and is passed as `dwPort`; both arguments for `dwSlot` and polling parameters are zero when it calls `XInputOpen` (`0x0027DE3B`). It stores the returned handle at `[0x003C9340 + port*0x90]` and calls `XInputGetState` (`0x0027E075`) for each non-null handle. The call at `0x001EBC74` passes that handle and a local state buffer at `ESP+0x28` (`text.asm`, `sub_001EBBE0`, `0x001EBBE0..0x001EBE07`).

`sub_0027E075` takes `(hDevice, pState)` and returns a status in EAX (`ret 8`). It reads the per-handle class context from `hDevice+0xA3`, rejects a context error flag with `0x57`, and returns `0x48F` when the opened device record is absent/invalid. On the successful path it writes the packet DWORD from the port/slot record at `hDevice+8` to `pState+0`, then copies the input bytes from `hDevice+0x14` to `pState+4`. Copy size is a runtime byte loaded from `*(*(hDevice+0xA3)+8)`; this function does not hard-code a report size (`XPP.asm`, `0x0027E075..0x0027E0E8`). The caller does not branch on the return code before reading the output, so an observer that acknowledges a transition should require `EAX == 0`; call entry or a non-error-looking output buffer is insufficient.

The consumer reads an 18-byte Xbox gamepad body: a WORD at `pState+4` (buttons), eight bytes at `pState+6..+13`, and four signed WORDs at `pState+14,+16,+18,+20` (`text.asm`, `0x001EBC79..0x001EBD54`). The Xbox-format `XBOX_GAMEPAD` is exactly this shape—`wButtons`, `bAnalogButtons[8]` (A, B, X, Y, Black, White, L/R triggers), and four thumb-axis SHORTs—(`xboxrecomp-input-latency/src/input/xinput_xbox.h`, `XBOX_GAMEPAD`). So the typed state buffer is 22 bytes total: packet DWORD plus 18-byte Xbox body. This is not Windows `XINPUT_GAMEPAD`'s two-trigger/12-byte layout. The API implementation still takes its copy count from the class-context length byte rather than a constant; for safe tracing, capture that actual length and bound it to the 18 bytes the gamepad caller consumes. The emulator's USB wire report is 20 bytes: two leading bytes (`0`, `20`) followed by those 18 gamepad bytes (`usb_gamepad.c`, `usb_gamepad_report`, `out[0..19]`). The XDK-side transfer/DPC path that strips or interprets that two-byte USB prefix is not established in this bounded audit; keep the API state buffer and USB packet formats distinct.

The handle can be mapped to a guest port without treating its address as a player number. `sub_001EBBE0` creates handles for `dwPort=0..3`, `dwSlot=0`. `XInputOpen` resolves the port key through `sub_0027ED74`: the opened-device table entry points at a lower USB handle; `sub_0027FE4F` returns that lower handle's `+0x14` port value, which is compared with the requested port. The returned table entry is stored at `hDevice+0` (`XPP.asm`, `sub_0027ED74` and `sub_0027F895`). Therefore a successful read identifies the guest `dwPort` associated with that handle; slot is known as 0 for this poller. A robust observer should retain this association when the handle is opened, or resolve the opened record under the XDK's own mapping, rather than infer port from host device index or handle pointer value.

For the configured one-pad case the host route is explicit: `usb_gamepad_report` pad 0 is driven by host XInput pad 0; `RECOMP_PAD_PORT` defaults to game port 1; `s_game_port_to_root={2,3,0,1}` routes that game port to OHCI root-port index 2 (third root port) (`usb_gamepad.h`, pad-index comment; `ohci.c`, `pad_root_port`). The permutation's comment identifies the inverse relationship: root port index 0 is Def Jam player 3, so root index 2 is the game's player/game-port 1. XPP creates four root-port device objects in a zero-based `ESI` loop and stores that index at object `+4` (`sub_0027CF80`, `0x0027CFFA..0x0027D065`). This configuration suggested guest `dwPort=2`, `dwSlot=0` for the default host pad, but that was a route expectation, not a proved runtime mapping. In the later corrected-trigger baseline, X rises were observed on guest XDK handle-array ordinal 0; retain that as runtime evidence separately from the toolkit root-port permutation. The local analysis still does not show the instruction that writes lower USB handle `+0x14`, which `sub_0027FE4F` compares against `dwPort`. A safe API hook should use the stored handle/record association or runtime key rather than infer from host pad or OHCI root index. Fighter slot remains a separate mapping.

## What is and is not connected to the fighter pad table

The CPU/AI handoff is `sub_001AD380`, called by `sub_000C89D0` from match update `sub_0008BE60`. It reads eight source records at `0x003BFA10 + slot*0xB8`; the actor guard tests bit 0 at actor+`0x937` and skips when clear, and existing telemetry identifies that bit as CPU control. When set, it maps the AI slot through `0x003B9098` and copies six DWORDs into that pad-table row. This is not the human input producer. Human pad input is written by `sub_0002D9E0`; see the corrected match-path findings below. `sub_001BAA00` reads the pad-table row at `0x003B8F48 + 0x20*MEM32(0x003B9098 + actorSlot*4)` (table stride 0x20).

The XInput poller's records at `0x003C9340` are a separate area. The bounded static xrefs show `sub_001EBBE0`/related poller code using that area and `sub_001AD380` reading `0x003BFA10` (AI-only); those are separate paths. A successful guest `XInputGetState` is still not the acknowledgement boundary for human fighter consumption. Keep guest handle ordinal, controller-manager index, Def Jam actor slot, and pad-table row separate unless their runtime mapping is directly observed.

## Evidence limits and instrumentation implication

- Pin a read to the guest handle's opened-record port key and accept it only when `sub_0027E075` returns success. Capture packet number plus the 18-byte Xbox-format body; preserve the actual runtime length byte as metadata rather than assuming it.
- Keep the guest port key, toolkit host pad index, Def Jam logical controller/player index, and fighter pad-table slot as separate identifiers. The available disassembly proves their local transforms but not the complete chain joining them.
- A successful `XInputGetState` is proof that the XDK API copied a snapshot to its caller, not proof that the fighter cache or fighter routine consumed that transition.
- Existing 20–22 ms trace numbers are observed boundary delays. The uninstrumented XDK-read and `0x003BFA10` update boundaries remain the next points needed to localize this interval.

## Correction: human match-path writer and acknowledgement boundary

The match wrapper `sub_000C89D0` is AI-only in this context: it calls `sub_001AD380`; that routine checks actor+`0x937` bit 0 (`0x001AD3B9..0x001AD3BD`) and skips the actor if the bit is zero. Existing fighter-record telemetry identifies bit 0 as CPU/AI control, so the earlier description of this as the fighter-side (human) handoff was incorrect.

The human pad-table producer is `sub_0002D9E0`. Its caller `sub_0002DFF0` invokes it at `0x0002E024..0x0002E026`, then calls match update `sub_0008BE60` at `0x0002E067..0x0002E06D`. `sub_0002D9E0` establishes table base `0x003B8F48` through `sub_001A32E0` (`0x0002D9ED..0x0002D9F7`; `sub_001A32E0` stores that base at context+4, `0x001A32E4..0x001A32EB`), resolves controller manager component `0x19`, iterates controller indexes 0..7, gets each device via `sub_000DCBA0`, and skips disconnected devices (`sub_0002DA20..0x0002DA40`). For active devices, it writes the button word to `tableBase + sub_000DC4C0(index)*0x20` (`0x0002DA40..0x0002DA63`), the second button word at +4 (`0x0002DA63..0x0002DA7B`), and four stick floats at +8,+0xC,+0x10,+0x14 via `sub_000DD3C0` (`0x0002DA7F..0x0002DAD1`). Thus the human route is controller manager/device polling -> `sub_0002D9E0` pad-table writes -> `sub_0008BE60` -> per-fighter `sub_001BAA00` reads.

The human reader `sub_001BAA00` uses `actor+0x28` to get the actor's controller slot, looks up that slot through `0x003B9098`, and computes the pad-table row `0x003B8F48 + mappedSlot*0x20` (`0x001BAA3C..0x001BAA50`). It reads buttons and stick values from this row and updates the actor's held/pressed caches (`0x001BAA6E..0x001BABxx`). This supports fighter-read acknowledgement at `sub_001BAA00` for the actor's mapped row. It does not make the unrelated guest `XInputGetState` call a safe acknowledgement boundary. Runtime observation reported X rising on guest XDK handle-array ordinal 0; that runtime result should be kept distinct from the toolkit's configured root/game-port permutation until a direct live mapping connects them.

Bounded stop: the executable disassembly establishes the human producer and consumer wrappers and their table transform, but this read-only pass does not prove which specific underlying controller-manager getter ultimately consumes the USB-backed guest XInput snapshot. The per-fighter table read is the currently supported human acknowledgement point. `0x3BFA10`/`sub_001AD380` should be treated as CPU/AI state only.

## PAD_TABLE button-mask transform

Do not use the debug-menu accessor mask as the `PAD_TABLE` mask. The human writer `sub_0002D9E0` calls `sub_000DD2B0(device, 0)` to obtain the accessor's held word, passes that word through `sub_000DC4F0`, and writes the transformed result to table word 0 (`0x0002DA40..0x0002DA63`). `sub_000DC4F0` explicitly performs a bit transform (`0x000DC4F0..0x000DC54E`). Composing its source instructions with the accessor meanings recorded by the checked debug-menu audit yields these PAD_TABLE masks; runtime trigger trace independently confirms LT+RT -> `0x3000` and X -> `0x40`:

| Control | accessor mask (input to `sub_000DC4F0`) | PAD_TABLE word 0 (output) | Basis |
| --- | ---: | ---: | --- |
| LT / RT | `0x01` / `0x04` | `0x1000` / `0x2000` | Source transform; runtime trace confirms combined `0x3000` |
| White / Black | `0x02` / `0x08` | `0x0100` / `0x0200` | Source transform composed with accessor labels |
| A / B / X / Y | `0x10` / `0x20` / `0x40` / `0x80` | `0x0020` / `0x0010` / `0x0040` / `0x0080` | Source transform; X independently observed |
| Start / Back | `0x0100` / `0x0200` | `0x0800` / `0x0400` | Source transform composed with accessor labels |
| d-pad up/down/left/right | `0x1000` / `0x2000` / `0x4000` / `0x8000` | `0x0001` / `0x0002` / `0x0004` / `0x0008` | Source transform composed with accessor labels |
| left/right stick click | — | no mapped bit identified | Not read by this transform as click controls; no mapping found |

This is a two-layer result: the function proves how the accessor word becomes PAD_TABLE word 0; the named-control labels for the accessor bits come from the separate checked debug-menu audit and are not PAD_TABLE masks. Exact PAD_TABLE face+trigger mask `0x30F0` is consistent with this transform. No PAD_TABLE d-pad bits are action-remapped in `sub_001BAA00`; it derives its direction nibble from left-stick float magnitude/angle and passes the table's other bits onward. The two thumb sticks are written as four float fields at +8,+0xC,+0x10,+0x14 via `sub_000DD3C0`; `sub_001BAA00` derives direction bits from the left stick and sets active flags `0x10000`/`0x20000` based on left/right-stick magnitude. This audit does not establish stick-click support or that every host/backend produces the same accessor word.
