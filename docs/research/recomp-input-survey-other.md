# Recomp input survey: additional projects

Surveyed 2026-10-30. This is a source audit, not a latency benchmark. No game was run and no project was built. Candidate repos were retrieved from public GitHub and source snapshots are under `logs/input-audit/research/other/`. All claims below are limited to source/docs in the pinned commit. “Unknown” means the inspected code does not establish it.

## N64 input call path: state reads versus event pump

Banjo-Recompiled wires `recompinput::handle_events` to the graphics callback and `recompinput::poll_inputs`/`profiles::get_n64_input` to ultramodern’s controller callbacks ([host wiring, pinned source](https://github.com/BanjoRecomp/BanjoRecomp/blob/dbd52154bc1e00e56867b1fac94a8f907052f41b/src/main/main.cpp#L200-L202), [callbacks](https://github.com/BanjoRecomp/BanjoRecomp/blob/dbd52154bc1e00e56867b1fac94a8f907052f41b/src/main/main.cpp#L773-L778)). The pinned runtime is a gitlink, so its code is cited from the owning repository at runtime commit `ca568b6ad79b9029d14077f0c3ffa757727c5559`: the runtime invokes `update_gfx` in its outer loop after a 1 ms sleep ([loop](https://github.com/N64Recomp/N64ModernRuntime/blob/ca568b6ad79b9029d14077f0c3ffa757727c5559/librecomp/src/recomp.cpp#L887-L893)); that is an event-drain loop, not proof of game input sampling or presentation cadence. The guest-driven `osContStartReadData` callback calls `poll_input`, then the guest reads current state through `osContGetReadData` ([runtime read](https://github.com/N64Recomp/N64ModernRuntime/blob/ca568b6ad79b9029d14077f0c3ffa757727c5559/ultramodern/src/input.cpp#L107-L115), [state conversion](https://github.com/N64Recomp/N64ModernRuntime/blob/ca568b6ad79b9029d14077f0c3ffa757727c5559/ultramodern/src/input.cpp#L153-L173)). Thus guest poll cadence is determined by game code; source does not establish an absolute frequency or measured latency.

Trouble Makers uses its own SDL2 callback. On an N64 read, it pumps SDL, snapshots keyboard state, refreshes its single attached game controller, then samples buttons and axes using `SDL_GameControllerGetButton` and `SDL_GameControllerGetAxis` ([input backend, pinned source](https://github.com/ThiagoLira/trouble-makers-pc-recomp/blob/ef89277812f31895b2902cf4e61780f2dd021644/src/audio_input/input.cpp#L50-L105), [poll and read](https://github.com/ThiagoLira/trouble-makers-pc-recomp/blob/ef89277812f31895b2902cf4e61780f2dd021644/src/audio_input/input.cpp#L120-L175), [callback registration](https://github.com/ThiagoLira/trouble-makers-pc-recomp/blob/ef89277812f31895b2902cf4e61780f2dd021644/src/audio_input/input.cpp#L201-L227)). This is current-state sampling, not a gameplay edge queue. A press and release fully between guest polls can be missed; that follows from the implementation, not a reported play-test defect. Native simulation is 60 Hz and optional 240 Hz display interpolation is documented in the [pinned README](https://github.com/ThiagoLira/trouble-makers-pc-recomp/blob/ef89277812f31895b2902cf4e61780f2dd021644/README.md#L235-L245). Rendering interpolation does not establish faster guest sampling.

Banjo and Tooie use the shared RecompFrontend pattern: event handling responds to device add/remove and feeds binding/UI events; `poll_inputs` snapshots keyboard state; gameplay queries current button/axis state with SDL getters. Immutable source links are available for the [Banjo frontend pin](https://github.com/N64Recomp/RecompFrontend/blob/d0d90ba49f46f4896aaeda362056c21b1e342561/recompinput/src/input_state.cpp#L34-L57), and the same code is present directly in Tooie's [pinned source tree](https://github.com/Frostie77/Tooie-Recompiled/blob/d33657d17ba72f0df9c4654e1c476ef42aa432d9/lib/RecompFrontend/recompinput/src/input_state.cpp#L34-L57). The shared [button getter](https://github.com/N64Recomp/RecompFrontend/blob/d0d90ba49f46f4896aaeda362056c21b1e342561/recompinput/src/input_state.cpp#L137-L159), [axis getter](https://github.com/N64Recomp/RecompFrontend/blob/d0d90ba49f46f4896aaeda362056c21b1e342561/recompinput/src/input_state.cpp#L163-L203), and [hotplug handler](https://github.com/N64Recomp/RecompFrontend/blob/d0d90ba49f46f4896aaeda362056c21b1e342561/recompinput/src/input_events.cpp#L73-L105) show event-driven device lifecycle with current-state gameplay reads. Button-down/up events support binding/UI, but the game read path queries current state rather than consuming an ordered set of gameplay edges ([event cases](https://github.com/N64Recomp/RecompFrontend/blob/d0d90ba49f46f4896aaeda362056c21b1e342561/recompinput/src/input_events.cpp#L124-L137), [button-up path](https://github.com/N64Recomp/RecompFrontend/blob/d0d90ba49f46f4896aaeda362056c21b1e342561/recompinput/src/input_events.cpp#L152-L160)). The frontend also exposes remapping and a configurable deadzone ([implementation](https://github.com/N64Recomp/RecompFrontend/blob/d0d90ba49f46f4896aaeda362056c21b1e342561/recompinput/src/input_state.cpp#L316-L345)). Short gameplay taps remain subject to guest poll cadence.

Kirby 64 has the same architecture but a project-owned input file: `update_gfx` drains `SDL_PollEvent`; `poll_inputs` snapshots current keyboard/controller state; the guest API registers those callbacks ([event loop](https://github.com/Kirby64Ret/Kirby64Recomp/blob/480ed7e2a3160087bbe5f680f08e601eef7a4d69/src/game/input.cpp#L300-L319), [poll state](https://github.com/Kirby64Ret/Kirby64Recomp/blob/480ed7e2a3160087bbe5f680f08e601eef7a4d69/src/game/input.cpp#L468-L475), [callback wiring](https://github.com/Kirby64Ret/Kirby64Recomp/blob/480ed7e2a3160087bbe5f680f08e601eef7a4d69/src/main/main.cpp#L648-L653)). Hotplug is event-driven, while actual button/axis gameplay state is current-state querying. Its input behavior is useful code evidence but the project is WIP.

Banjo and Banjo-Tooie share RecompFrontend code lineage and ultramodern's `osCont*` callback model. Treat that behavior once, then distinguish project-specific patches/settings. Trouble Makers provides independent host input code but still inherits ultramodern's guest polling contract.

## Xbox fighting-game path: DBZ Burst Limit

DBZ calls the XInput API, but its SDK’s default backend is SDL3 (`input_backend=sdl`): `input_poll_on_read=true` asks SDL to update gamepads at the time of guest state reads, throttled to one update per 1 ms. The option’s documented off mode uses the last UI-thread update, which may be up to one frame old ([default and poll policy](https://github.com/iExplosiveRage/rexglue-sdk/blob/3c41e4b6debbaf0688cd7b9a99b4f365ca79655d/src/input/input_system.cpp#L29-L40), [SDL backend read path](https://github.com/iExplosiveRage/rexglue-sdk/blob/3c41e4b6debbaf0688cd7b9a99b4f365ca79655d/src/input/sdl/sdl_input_driver.cpp#L358-L402)). SDL device changes enter through event handling and are reconciled on state acquisition ([device setup and mapping file](https://github.com/iExplosiveRage/rexglue-sdk/blob/3c41e4b6debbaf0688cd7b9a99b4f365ca79655d/src/input/sdl/sdl_input_driver.cpp#L237-L277), [device enumeration/reconciliation](https://github.com/iExplosiveRage/rexglue-sdk/blob/3c41e4b6debbaf0688cd7b9a99b4f365ca79655d/src/input/input_system.cpp#L97-L187)). The SDK merges assigned devices and applies configurable stick deadzones ([state acquisition and transition log](https://github.com/iExplosiveRage/rexglue-sdk/blob/3c41e4b6debbaf0688cd7b9a99b4f365ca79655d/src/input/input_system.cpp#L285-L335), [deadzone](https://github.com/iExplosiveRage/rexglue-sdk/blob/3c41e4b6debbaf0688cd7b9a99b4f365ca79655d/src/input/input_system.cpp#L496-L530)). Its optional XInput backend does a synchronous `XInputGetState` per guest state read ([driver sampling](https://github.com/iExplosiveRage/rexglue-sdk/blob/3c41e4b6debbaf0688cd7b9a99b4f365ca79655d/src/input/xinput/xinput_input_driver.cpp#L190-L229)); input focus suppression is evident in the SDL driver but not in that XInput read path. Neither backend establishes device hardware report rate. The SDK’s latency instrumentation marks when a button first appears in successive guest reads; that is a guest-visible transition, not end-to-end device-to-photon latency.

This project explicitly separates controller sampling from game logic’s intentional frame delay. Its patch docs state offline fights normally consume input three game frames (50 ms at 60 Hz) late; `input_delay=reduced` changes the consumed frame to the one written on the current tick. Online `online_input_delay` is a distinct frame delay (2–8 or game default) and an optional channel transmits unconfirmed frame-keyed inputs early ([settings/source comments](https://github.com/iExplosiveRage/DBZ-Burst-Limit-Recompiled/blob/8faff03f1cc316e123339111c3f7364876e63ab8/src/burstlimit_netinput.cpp#L46-L65), [offline and online frame consumption](https://github.com/iExplosiveRage/DBZ-Burst-Limit-Recompiled/blob/8faff03f1cc316e123339111c3f7364876e63ab8/src/burstlimit_netinput.cpp#L589-L630), [README explanation](https://github.com/iExplosiveRage/DBZ-Burst-Limit-Recompiled/blob/8faff03f1cc316e123339111c3f7364876e63ab8/README.md#L175-L190)). Those are emulated game/network buffering policies, not controller acquisition latency. The source does not establish whether a sub-frame tap between guest state reads is latched; XInput current-state reads imply it may be lost unless game or SDK buffering retains it. No measured claims are made here.

The SDK default is SDL; XInput is a configurable Windows alternative ([backend default and selection](https://github.com/iExplosiveRage/rexglue-sdk/blob/3c41e4b6debbaf0688cd7b9a99b4f365ca79655d/src/input/input_system.cpp#L29-L40), [driver registration](https://github.com/iExplosiveRage/rexglue-sdk/blob/3c41e4b6debbaf0688cd7b9a99b4f365ca79655d/src/input/input_system.cpp#L636-L665)). The app passes a focus/overlay active callback into the input system ([callback setup](https://github.com/iExplosiveRage/rexglue-sdk/blob/3c41e4b6debbaf0688cd7b9a99b4f365ca79655d/src/ui/rex_app.cpp#L857-L867)). The SDL controller driver returns neutral state while inactive and preserves the held controller state to show again after activation ([active SDL read behavior](https://github.com/iExplosiveRage/rexglue-sdk/blob/3c41e4b6debbaf0688cd7b9a99b4f365ca79655d/src/input/sdl/sdl_input_driver.cpp#L358-L402)). Its device refresh tracks stable guest ordinals through removal/reconnection; mappings can be supplied by a gamecontroller DB file. The XInput alternative enumerates four fixed native slots and obtains states via the OS API. Remapping and deadzone options exist, but the defaults are not evidence of fighting-game optimality.

## SDL3 reference and recommendations for Def Jam

The surveyed N64 code uses SDL2; DBZ’s SDK uses SDL3 by default for gamepads and offers XInput as a Windows alternative. SDL3’s `SDL_GamepadButtonEvent` has ordered button-down/up events, a joystick instance ID, and a nanosecond timestamp populated from `SDL_GetTicksNS`: [official SDL3 event docs](https://wiki.libsdl.org/SDL3/SDL_GamepadButtonEvent). `SDL_PollEvent` removes the next queued event and the documented pattern drains the queue before updating game state: [official SDL3 polling docs](https://wiki.libsdl.org/SDL3/SDL_PollEvent). SDL says `SDL_PollEvent` should only run on the main thread; its remarks add that it may call `SDL_PumpEvents`, which SDL also restricts to the main thread (and, in the remarks, the thread that initialized video). SDL does not document an exception for a native Win32 window or gamepad-only initialization, so keep event polling on the process main thread. SDL separately says `SDL_UpdateGamepads` and `SDL_UpdateJoysticks` are safe from any thread. `SDL_SetJoystickVirtualButton` is also callable from any thread, but its change does not become visible until `SDL_UpdateJoysticks` runs (thread-safe) or another joystick-updating API is called: [UpdateGamepads](https://wiki.libsdl.org/SDL3/SDL_UpdateGamepads), [PumpEvents](https://wiki.libsdl.org/SDL3/SDL_PumpEvents), [PollEvent](https://wiki.libsdl.org/SDL3/SDL_PollEvent), [SetJoystickVirtualButton](https://wiki.libsdl.org/SDL3/SDL_SetJoystickVirtualButton), [UpdateJoysticks](https://wiki.libsdl.org/SDL3/SDL_UpdateJoysticks). SDL recommends performance-counter or nanosecond ticks for timing instead of millisecond `SDL_GetTicks`: [official timing FAQ](https://wiki.libsdl.org/SDL3/FAQDevelopment). These semantics are SDL3-specific; do not project them onto the SDL2 N64 projects.

For a 60 Hz simulation, event delivery and device reporting should be captured separately from simulation sampling and render/present. Keep latest held state for continuous movement and queue button-down/up edges with timestamps until a simulation tick consumes them; otherwise current-state polling can discard a press shorter than one guest sample interval. Drain host events promptly on the main thread. Measure the fixed-step cadence and the event-to-consume delay; never infer controller hardware report rate from app poll frequency or render FPS. Track focus policy, hotplug/reconnect IDs, remapping, and per-axis deadzone separately. The code audited here supports these recommendations, but does not itself provide a comparative measured latency result.
