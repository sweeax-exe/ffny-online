## Concrete behavior supported by inspected code

The four Zelda-lineage repos (Zelda, Star Fox, Mario Kart, Smash) register `recomp::poll_inputs` and `recomp::get_n64_input` with the runtime. In the runtime, `osContStartReadData` calls the poll callback, while `osContGetReadData` separately calls the get callback to fill N64 button and stick fields. This distinction matters: the host is not simply sampling on window refresh or render present, but sampling when guest code requests controller reads. The exact request frequency is game-code behavior and is not established by these callback definitions.

The Zelda-lineage host callback copies keyboard key-state and currently open controller handles. Subsequent button/axis helpers call SDL `SDL_GameControllerGetButton` and `SDL_GameControllerGetAxis`; the helpers operate on levels, not accumulated button edges. Thus a short press that begins and ends between guest read requests is not guaranteed to appear in a report. This is a source-level inference from the level-query implementation, not a measured dropped-tap result. SDL controller add/remove events maintain the controller list. SDL event processing uses `SDL_PollEvent`; rendering and event processing cadence was not shown to be the controller input cadence.

DKR-R is materially different: its platform poll function explicitly calls SDL update before querying devices; loops four player profiles; checks overlay blocking and window input focus, with configurable background controller input; and uses a configurable deadzone/sensitivity/curve pipeline. It also has SDL3 snapshot support. This is stronger configurability evidence than the Zelda-lineage projects, but no physical latency measurement is present.

No source path provides measured button-to-simulation or button-to-photon latency. `measure_input_latency()` in N64ModernRuntime is disabled under `#if 0` and only measures elapsed time since the last poll at a later call; it is not an external end-to-end measurement even if enabled.

## Independence accounting

These five projects are not five independent validations. Zelda, Star Fox, Mario Kart, and Smash share the N64ModernRuntime family and carry close copies of the same project-level input adapter; each has a different pinned runtime SHA. Smash is a fork of Zelda64Recomp and is especially non-independent. DKR-R's own input implementation is a distinct path. For fighting-game design guidance, treat this as one family-level observation about the N64Recomp callback architecture plus one distinct DKR-R example, not as five votes.
