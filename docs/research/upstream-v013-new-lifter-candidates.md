## Flag-state work: split by dependency, not by incidental diff hunks

The current integration spans fork integer dynamic validity plus newly modeled PF, SSE/x87 publication, SAHF/LAHF, and upstream #159 edge planning. These should not be offered as independent unrelated PRs that each assume absent flag locals.

1. **Publish and consume path flags for supported integer producers** is the foundation already carried by fork replay `4a0eb5f` and `c1b3d26` (original `0352cc7` / `8e5c73b`). Unknown CFG joins and zero-count shifts must consume the flags of the executed producer, not reconstruct an answer from overwritten operands or from the nominal last shift. Include validity rules for partial/unsupported producers and independent compiled fixtures. This is a broader held generic topic, not a new v0.13-only one-line fix.
2. **Extend that foundation to parity and architectural float/SAHF interactions.** SSE COMI instructions publish ZF/CF/PF and clear SF/OF; FCOMI-family EFLAGS must survive later x87 status-only FCOM; SAHF must read actual AH rather than g_fp_cmp and preserve OF; LAHF must read the available architectural flag snapshot. Pristine source independently exposes SAHF as a no-op plus g_fp_cmp-based static interpretation, and FCOMI -> FCOM overwrites the same g_fp_cmp consumed later as EFLAGS. However, the current solution depends on the dynamic locals/validity foundation. Either stage it after that foundation or design a separate minimal EFLAGS snapshot implementation for upstream; do not copy the dependent hunks into pristine upstream as if self-contained.
3. **Reconcile #159 with the shared condition interface.** Pristine #159 resolves only the first flag reader at a disagreeing join; later SET/CMOV/LAHF consumers retain fallback/state limitations. In the fork union, matching `_flags /* mnemonic>` and `fallback flag var` fails because dynamic predicates/declarations differ. Candidate now identifies consumer instructions explicitly and uses shared `flag_condition` instead of replacing generated strings. That clean-up is necessary integration, but the missing substring itself is a fork-only compatibility failure, not a pristine upstream defect. Submit with the state foundation/extension, together with mixed integer/SSE multiple-consumer tests, and retain upstream exclusions for unseen edges, unknown predecessors and live-register hazards.
