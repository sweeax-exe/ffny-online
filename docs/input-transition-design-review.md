# Input-edge implementation review

Read-only review of the current working tree. The toolkit submodule and guest adapter have uncommitted changes; this records observed behavior, not a clean-commit review. No code edits, builds, or game runs were made.

## Actionable findings

1. **Focus/UI cancellation can be undone by an in-flight poll (confirmed race).** `poll_once` snapshots `focused` and `ui_active` before sampling (`tools/xboxrecomp/src/input/input_host.c:517-529`), then later feeds or resets the queue using those old locals (`:565-584`). UI/focus setters publish the new state and separately cancel queues (`:1029-1035`, `:1080-1091`). Interleaving: poll captures focused/UI-closed; UI opens and empties the queue; the old poll then enters `H.cs` and feeds its pre-overlay state. `xbox_HostInputPeekState` checks slot presence but does not gate the read on current focus/UI state (`:1099-1123`), so USB can deliver that newly requeued command before a later host poll clears it. Keep activation/focus change, queue reset and poll eligibility synchronized under `H.cs`; recheck eligibility at queue feed and at state peek, returning neutral while game input is disabled. Respect `ignore_focus`.

2. **Class control GET_REPORT can expose an edge without a delivery token (confirmed untracked path).** The gamepad control handler builds its report through `usb_gamepad_report` (`tools/xboxrecomp/src/usb/usb_gamepad.c:162`), which delegates to `usb_gamepad_report_peek(..., NULL)` (`:809-829`). In consumed-edge mode this still selects a queued edge snapshot, but no token reaches the control caller. OHCI only calls `usb_gamepad_report_delivered` for interrupt-IN reports after successful TD completion (`tools/xboxrecomp/src/usb/ohci.c:942-975`); endpoint-0 GET_REPORT goes through `usb_gamepad_control`/`ohci_do_td` without `report_pad` or token delivery. Consequently a successful control GET_REPORT cannot mark that edge delivered, so a later XDK packet cannot retire it through the `delivered` predicate. It will stay pending until a later interrupt delivery or the 100 ms expiry. Either make control GET_REPORT snapshot-only, or carry a token and mark it delivered only after the complete successful control data stage. Include a control-GET_REPORT fixture.

3. **Analog edges use “nonzero” as the press threshold (policy mismatch; consequence depends on the title).** `input_edges_mask` maps every nonzero analog byte to a pressed bit (`tools/xboxrecomp/src/input/input_edges.c:4-9`); the queue tests only exercise values 100/200 (`tools/xboxrecomp/tests/input_edges/test_main.c:55-61`). The toolkit's default trigger map threshold is 5% (`tools/xboxrecomp/src/input/input_map.c:308-310,366-374`), while its input API documents `XBOX_ANALOG_BUTTON_THRESHOLD == 30` as the recommended game-side pressed threshold (`tools/xboxrecomp/src/input/xinput_xbox.h:42`, `tools/xboxrecomp/src/input/README.md:31-32,113`). A 1..29 trigger pulse is therefore queued/ackable even for a title that treats it as released. This is not evidence of a Def Jam miss, but the transition criterion should be explicit: either use a per-control/game threshold with a defined release threshold (hysteresis if desired), or state that any analog magnitude change above zero counts. Add boundary cases around the selected threshold and ensure pressure changes while already pressed remain current-valued.

## Reviewed behavior that appears sound, with limits

The FIFO accepts 64 entries and expires a stale prefix after 100 ms; overflow resets to the current state and is counted (`input_edges.h:4-5`, `input_edges.c:22-49`). Its coalescing stops before a repeated transition of the same button (`:52-73`), preserves all 8 digital bits plus the 8 analog channels in the mask (`:4-9`), and keeps axes outside the edge mask. `input_edges_consume` rejects non-new packet numbers, then only removes a matching entry marked delivered (`:85-104`). The native fixtures cover rapid cycles, chords, failed/stale acknowledgement, age, overflow, reset, analog coalescing, packet wrap and ring reuse (`tests/input_edges/test_main.c:17-74`). The host queue operations and packet state are all inside `H.cs` (`input_host.c:565-587,1099-1156`); USB report peek releases that lock before the TD is attempted, and OHCI marks the token delivered only on `TD_CC_NOERROR` (`ohci.c:971-976`). A reset/expiry between peek and delivery simply makes the old token unfindable; tokens monotonically advance, so it cannot mark a replacement entry.

The packet guard assumes the guest's packet DWORD is a strictly advancing serial for each newly copied state. `input_edges` has direct wrap/stale tests, but the guest adapter supplies the packet from the XDK state buffer after a successful `sub_0027E075` (`src/hooks/input_latency_guest.c:37-55`, called by `src/recomp_manual.c:191-199`). That is an API-copy acknowledgement, not proven fighter/simulation consumption: [the existing consumption-boundary audit](research/input-consumption-boundaries.md) says the static xrefs do not establish the packet-record-to-fighter-cache bridge. Treat “guest XDK copy consumed” as the contract; do not claim the fighter acted on each queued edge without that bridge. An actual trace should confirm packet increments and stale-read behavior across consecutive queued reports and USB reset; no source-level packet-reuse bug was proven here.

The SDL worker change is sound with respect to the reported thread-affinity concern: it calls `SDL_UpdateGamepads` and `SDL_PeepEvents(SDL_GETEVENT)` rather than worker-thread `SDL_PollEvent` (`input_host.c:619-651`). SDL documents UpdateGamepads and PeepEvents as safe from any thread, while PollEvent is main-thread-only because it can pump events ([SDL_UpdateGamepads](https://wiki.libsdl.org/SDL3/SDL_UpdateGamepads), [SDL_PeepEvents](https://wiki.libsdl.org/SDL3/SDL_PeepEvents), [SDL_PollEvent](https://wiki.libsdl.org/SDL3/SDL_PollEvent)). The Windows worker drains gamepad button events only for tracing (`:631-639`); actual edge capture still comes from `poll_once`'s sampled `next[s]` state (`:577-582`). Thus a down/up that starts and ends between two host polls (default poll period is 2 ms, `:44-45,913-915`) is not preserved by the FIFO. That is the sampler's finite-resolution limit, not a queue ordering defect; a targeted source-integration fixture or SDL-event-backed edge feed would be needed to claim sub-poll tap capture.

## Follow-up review of the current fix

The focus/UI epoch recheck now prevents a poll that began before a focus/UI transition from publishing its stale non-neutral sample: `poll_once` snapshots the epoch before sampling and clears `next` when it changed before the locked publish (`xboxrecomp-input-latency/src/input/input_host.c:521-529,573-577`). UI/focus setters bump the epoch, and the state peek now independently returns neutral while UI is active or focus is lost (`:1069-1077,1123-1137,1145-1160`). **One edge case remains:** the epoch mismatch branch clears input even when `H.cfg.ignore_focus` is true (`:573-575`), while `live = focused || cfg.ignore_focus` explicitly permits background input (`:532`). A focus transition overlapping one poll therefore drops/resets that sample in ignore-focus mode. Narrow the mismatch cancellation to UI changes or effective focus loss, preserving the sample when ignore-focus is enabled.

Class GET_REPORT is now snapshot-only in consumed-edge mode (`xboxrecomp-input-latency/src/usb/usb_gamepad.c:161-166,841-846`), so it no longer exposes an untracked queued edge. Interrupt-IN still obtains a token at peek and marks it delivered only after successful TD completion (`:817-838`, `xboxrecomp-input-latency/src/usb/ohci.c:942-943,972-976`). The Def Jam adapter sets the analog edge threshold to 1 and classifies those action bytes with `> 1` (`src/hooks/input_latency_guest.c:22-34`), aligning its edge mask with the inspected game-side predicate.

**Correction: the proposed pending-ACK overwrite loss is not reachable through the normal queue path.** Although the adapter has one pending record per port and XDK completion replaces it (`src/hooks/input_latency_guest.c:114-119`), `input_edges_peek` stops before a repeated button-bit transition (`xboxrecomp-input-latency/src/input/input_edges.c:55-72`). Thus once a press is offered, its release cannot be offered to XDK until a matching delivered packet is consumed. A divergent release is possible after expiry/cancel/overflow, which intentionally drops the stale queue and resynchronizes to latest; it should not then preserve the expired press. The earlier press-then-release overwrite claim above this line is withdrawn. An out-of-order old XDK completion can temporarily replace pending metadata, but `input_edges_consume` rejects non-new packets (`xboxrecomp-input-latency/src/input/input_edges.c:91-94`), and I found no demonstrated path by which that completion retires a newer queued transition. Concurrent completion order remains a useful stress-test case rather than a confirmed loss bug. The existing `pending_lock` serializes adapter access, and calls into the host queue occur under that lock; no reverse `H.cs` to `pending_lock` acquisition was found in the reviewed call paths.
